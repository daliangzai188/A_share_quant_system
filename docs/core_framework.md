# A股量化系统核心框架基准

最后更新：2026-08-22

## 一、文档定位

本文固定当前系统的核心设计思想，作为后续逐步优化的共同基准。它描述的是整个
系统如何从数据走到候选、计划、委托、成交、持仓和发布认证，不是某一条策略的
回测说明。

后续可以优化模块实现，但不能在没有单独论证、回归和文档更新的情况下破坏本文
列出的核心不变量。若文档与代码、配置或严格认证结果发生冲突，必须立即停止新BUY，
查明口径后再恢复。

## 二、核心目标

系统的目标不是让四条策略各自展示一条漂亮收益曲线，而是建立一套能够被复现、
审计和安全执行的A股单账户交易闭环：

```text
严格时点数据
    ↓
候选特征与成交可靠性
    ↓
A/C/D/E各自的策略判断
    ↓
D>A>E>C统一资金裁决
    ↓
A股规则与风险门禁
    ↓
唯一委托通道
    ↓
券商成交确认与持仓账本
    ↓
执行复盘、严格认证和发布门禁
```

系统优先级固定为：

```text
数据准确 > 时点真实 > 资金不重复 > 风控安全 > 可执行性 > 回测收益
```

## 三、当前锁定口径

当前正式研究锚点如下：

| 项目 | 当前口径 |
|---|---|
| 严格窗口 | `20240630~20260630` |
| 首个可用信号日 | `20240701` |
| 组合腿序 | `D>A>E>C` |
| 资金模型 | 单账户、逐笔机械复利、持仓期间不重复使用资金 |
| 目标仓位 | 82.5% |
| 单票硬顶 | 85% |
| 最大持仓数 | 1 |
| A/C/E买入 | T日收盘选股，T+1开盘执行 |
| D买入 | 信号日盘中严格路径触发 |
| 交易规则 | T+1、涨跌停、停牌、费用、滑点、成交可靠性 |
| 当前协议 | `STRICT_DISCOVERY` |
| 当前发布资格 | `release_eligible=false` |
| 当前新BUY | fail-closed关闭 |

旧窗口305.348870倍和五年重放343.5434倍不属于当前严格锚点，不能用于当前策略

当前严格研究组合为132笔、327.726719倍机械复利、最大回撤-22.9705%，分腿实际

真实资金容量承诺。

## 四、七层核心架构

### 1. 数据层

数据层负责回答“在当时真实能够知道什么”，不负责决定买哪只股票。

主要职责：

- 采集日线、前复权行情、涨停池、日基本面、市场情绪和题材数据；
- 尽量包含退市股票，降低幸存者偏差；
- 保存原始数据，支持按日期补采、断点续传和重复运行；
- 对交易日期、股票代码、重复行、缺失值和异常价格进行清洗；
- 记录数据来源、可用日期和口径，禁止把晚发布数据提前到信号时点。

关键原则：

```text
原始数据不可被策略脚本反向改写。
缺失数据不能用未来数据回填。
完整口径缺失时不能静默退回宽松口径。
```

### 2. 特征与成交可靠性层

该层把原始数据转换成T日可见的市场、板块和个股特征，并评估候选是否具有现实
成交可能性。

主要内容：

- 涨停数量、跌停数量、连板数量和市场退潮状态；
- 板块涨停数量、板块情绪和题材热度；
- 首次涨停时间、炸板次数、连板高度和封单比例；
- 换手率、成交额倍率、量比和流通市值；
- 严格as-of成交空间及`fill_probability`；
- `allow_buy_reliable`、`is_fill_score_reliable`和数据质量标记。

成交概率不是收益因子，而是可执行性门禁。涨得好的股票如果历史上基本买不到，
不能按理想成交计入可执行收益。

### 3. 策略候选层

候选层只回答“各策略按自己的规则看中了谁”，不应自行分配组合资金。

当前四条腿的角色：

| 策略 | 当前角色 | 主要时点 |
|---|---|---|
| D | 盘中首板回封策略，组合最高优先级 | 09:30起记录路径，14:00后允许BUY |
| A | 收盘主策略，偏低热度环境的综合得分与连板高度排序 | T日收盘 |
| E | 40条R1场景并集、板块neutral、换手率降序 | T日收盘 |
| C | A无正式选中时生成计划、组合中低于E的龙头补位策略 | T日收盘 |

必须区分以下对象：

```text
候选：策略规则筛选后的股票。
第一候选：该策略内部排序后的第一名。
正式信号：通过策略自身门禁、允许进入组合裁决的信号。
计划单：组合层分配资金后生成的待执行计划。
委托：已经提交到券商的订单。
成交：券商确认的真实成交数量和价格。
持仓：成交确认后写入统一持仓账本的资产。
```

候选不等于正式信号，正式信号不等于计划单，计划单不等于委托，委托也不等于
成交。日志和报告不得混用这些概念。

当前实现中，存在任何未平仓持仓、A已有计划或D当日已成交时，E不会生成正式信号，
但会执行只读候选检查并记录候选数和第一名。这解决了“E没有候选”和“E没有计算”
无法区分的问题，但也说明当前候选生成与资金优先级尚未完全解耦，属于后续可优化项。

### 4. 组合资金裁决层

组合层是整个系统的核心。四条策略不能各自拥有一份独立资金，最终必须进入同一个
单账户状态机。

固定裁决顺序：

```text
券商/本地仍有策略持仓
    → 禁止任何新开仓

账户确认空仓
    → D已成交或占用资金：其余腿不买
    → 否则A有正式计划：选择A
    → 否则E有正式计划：选择E
    → 否则C有正式计划：选择C
    → 全部没有：保持空仓
```

核心不变量：

- 每天最多形成一个实际开仓方向；
- 上一笔未退出前不得复用同一资金；
- 低优先级策略执行失败后不能擅自切换为过期的其他策略计划；
- 展示层可以列出所有候选，但不得重新解释优先级或参与下单；
- 理论计划与券商真实持仓冲突时，以经过完整性认证的券商状态为准；
- 状态未知时保持空仓，不做乐观推断。

### 5. 交易执行层

执行层只负责把组合层已经批准的唯一计划安全地送到市场，不负责重新选股。

必须执行的检查：

- 是否为交易日和允许的交易时段；
- 是否已有持仓、未完成委托或同票风险暴露；
- 是否超过82.5%目标仓位、85%硬顶或单笔限额；
- 是否满足最小成交可靠性和退出容量限制；
- 是否违反T+1；
- 涨停是否可以买入、跌停是否可以卖出；
- 是否存在重复订单、陈旧计划或过期执行窗口；
- 严格发布证书是否允许新BUY。

所有真实订单必须经过唯一券商适配器和统一下单网关。策略脚本、播报脚本和研究
脚本不得绕过网关直接下单。

### 6. 成交、持仓与恢复层

系统资金状态必须由真实成交驱动，而不是由“下单成功”或“计划生成成功”驱动。

核心流程：

```text
提交委托
    ↓
查询订单状态与真实成交量
    ↓
按成交分片写入持仓账本
    ↓
生成T+1可卖日期和计划退出日期
    ↓
到期平仓、撤单、残单补挂
    ↓
再次以券商余仓确认是否真正清空
```

恢复原则：

- daemon重启后先恢复券商连接和状态，不盲目补单；
- 本地账本缺失时只能依据经过完整性校验的券商快照恢复；
- 单轮查询异常不能直接把本地持仓标记为已清空；
- 未知成交数量按可能占用资金处理；
- D缺少09:30起完整盘中路径时，不能用午后快照伪造可交易信号；
- 状态文件损坏、分歧或版本落后时必须修复或fail-closed。

### 7. 审计、回测与发布层

研究结果和实盘发布是两个不同阶段。

严格回测必须同时满足：

- 信号只使用当时可见数据；
- 单账户占仓期间不重复使用资金；
- 统一费用、滑点、涨跌停和T+1规则；
- 候选池指标、独立策略指标和组合实际成交指标分开报告；
- 输入文件、代码文件和配置文件可哈希复现；
- 规则变化后从锁定底座逐腿替换，不能混用旧口径。

当前发布门禁：

```text
strict_asof_passed=true
并不等于
release_eligible=true
```

只有完成冻结样本外、walk-forward、容量验证、连续模拟盘和发布复核后，才能考虑
解除新BUY门禁。SELL、撤单和已有持仓退出不应被新BUY门禁阻断。

## 五、日常运行闭环

### 收盘流水线

```text
采集数据
→ 清洗合并
→ 市场/板块特征
→ 成交概率打分
→ 增强因子
→ A/C候选与计划
→ E候选/信号状态
→ 健康度和执行审计
→ ACDE候选产物只读统计
→ 组合计划播报
```

收盘候选统计只读取当日产物，不重新运行策略、不改变`D>A>E>C`、不生成委托。
产物缺失必须显示“未知”，不能误报为“候选0只”。

### 次日执行

```text
启动恢复与持仓核对
→ 组合状态机读取当日有效计划
→ 盘前容量和价格复核
→ 竞价/开盘执行
→ 成交确认与残单处理
→ 盘中D状态与持仓监控
→ 到期平仓和收盘看门狗
→ 执行完成率、滑点和真实收益复盘
```

## 六、核心安全不变量

以下规则属于框架级约束，不得因单次回测收益提高而绕过：

1. 禁止未来函数和结果字段参与选股。
2. 禁止候选池逐笔相乘冒充独立单账户复利。
3. 禁止四条策略分别假设拥有同一份完整资金。
4. 禁止持仓未确认清空时开新仓。
5. 禁止把委托受理当成真实成交。
6. 禁止涨停默认买入、跌停默认卖出。
7. 禁止T日买入后T日卖出。
8. 禁止过期计划在错过窗口后追补。
9. 禁止策略脚本绕过统一下单网关。
10. 禁止数据、证书或状态未知时乐观放行。
11. 禁止用旧窗口或旧输入哈希替代当前严格锚点。
12. 禁止把`STRICT_DISCOVERY`结果描述为可发布实盘收益。

## 七、当前已知短板

### 1. 研究与过拟合风险

A和E的新排序来自当前两年窗口内269个唯一排序变体搜索。虽然通过了“独立腿复利
提高”和“只替换该腿时组合复利提高”的双门槛，但仍属于同窗口发现，缺少真正冻结
后的前向样本外证据。

### 2. 候选层与资金层仍有耦合

理想结构应当是每条策略先独立输出不可变候选/正式信号，再由组合层统一分配资金。
当前E在A、D或持仓占用时只计算只读候选，不生成正式信号，审计信息已经补齐，但
架构边界仍不完全纯粹。

### 3. 守护进程职责过重

`scripts/trading_daemon.py`同时承担调度、播报、状态恢复、组合计划、成交确认、持仓
同步和推送。功能完整，但修改影响面较大，是当前主要维护风险。

### 4. 真实成交与容量证据不足

集合竞价、分钟成交、盘口排队、极端涨跌停、资金规模变化和连续模拟盘尚未形成完整
认证闭环。当前机械复利不能直接外推到真实大资金。

### 5. 数据源与恢复仍需增强

核心策略仍高度依赖Tushare及本地缓存。需要继续完善多源核验、字段漂移告警、交易日
完整性检查和可恢复的数据版本管理。

## 八、后续优化顺序

后续优化必须一次只解决一类问题，建议按以下顺序推进：

### 阶段一：候选、信号、资金裁决彻底分层

- 为ACDE定义统一、不可变的候选和正式信号结构；
- 每条策略独立记录是否完成计算、候选数量和第一名；
- 组合层只消费正式信号，不参与候选生成；
- 展示层只读取结果，不影响组合状态。

### 阶段二：拆分守护进程

- 数据流水线调度；
- 策略信号服务；
- 组合资金状态机；
- 订单执行与成交确认；
- 持仓恢复与审计播报。

每拆一层都必须保持现有行为回归一致，不能同时修改策略规则。

### 阶段三：强化数据血缘

- 为每日策略输入生成清单和哈希；
- 对关键字段建立跨数据源校验；
- 明确每个字段的最早可用时点；
- 把“0只候选”“未运行”“读取失败”“数据不完整”分别编码。

### 阶段四：补齐真实执行模型

- 集合竞价真实成交率；
- 09:30后分钟级滑点；
- 涨停排队与开板回封成交概率；
- 跌停延期卖出和尾盘容量；
- 不同资金规模下的成交覆盖率和冲击成本。

### 阶段五：冻结样本外与发布认证

- 冻结ACDE规则和配置哈希；
- 按每年6月30日、12月31日执行半年更新；
- 最近24个月作为唯一规则搜索和更新决策窗口，不拆成18个月研究加6个月否决验证；
- 24个月之前的更早6个月只做旁路稳健性观察，不反向影响本轮决策；
- 新版本冻结后的未来6个月用于实际交易并积累真正前向样本外；
- 永久保留每个发布版本的半年样本外账本；
- 连续模拟盘验证；
- 达到发布标准后再讨论小资金实盘。

完整时间窗口、逐腿双复利门槛和版本账本定义见
[`strategy_update_framework.md`](strategy_update_framework.md)。

## 九、框架优化的验收规则

每一次框架优化都必须回答：

1. 修改的是数据、候选、组合、执行、持仓还是认证层？
2. 是否改变任何策略的入选股票或交易时点？
3. 是否改变`D>A>E>C`、82.5%仓位或单账户占仓？
4. 是否新增未来数据、乐观成交或资金重复使用？
5. 旧行为如何回归，新行为如何单测？
6. 是否需要重跑严格认证或刷新输入清单？
7. 失败时是否仍保持fail-closed？
8. 日志能否区分未知、未运行、0候选、计划、委托和成交？

如果一次修改同时改变策略条件、资金状态机和执行模型，应拆成多个独立阶段，分别
验证和提交，避免无法判断收益或风险变化来自哪里。

## 十一、当前结论

当前框架已经具备较完整的研究、组合资金、A股规则、订单安全和审计骨架。下一阶段
不应继续优先追求同窗口回测倍数，而应围绕以下三件事逐步提高系统质量：

```text
分层更清楚
真实成交证据更多
样本外发布标准更严格
```

本文作为后续框架优化的起点。每完成一个阶段，都应更新对应章节、测试证据和发布
状态，确保系统演进始终可解释、可回退、可复现。
